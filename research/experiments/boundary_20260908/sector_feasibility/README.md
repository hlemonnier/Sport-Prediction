Sector-completion nowcasting is feasible at modest cost using the **raw incremental TimingData stream**. Exporting `Sector1SessionTime` or `Sector2SessionTime` from a native FastF1 lap cache is insufficient: those timestamps can be backdated using later lap information. No model was fitted and no network request was made for this review.

The evidence comes from installed FastF1 3.8.3 and one cached Australian GP 2026 race. This is an input/engineering probe, not a model-selection event or a performance result. `probe.py` reads the existing HTTP SQLite cache in read-only mode and saves its source bindings and counts in `artifacts/research/boundary_20260908/sector_feasibility/probe.json`.

FastF1's raw HTTP cache contains the original timestamp-prefix/body bytes. The selected URL is `https://livetiming.formula1.com/static/2026/2026-03-08_Australian_Grand_Prix/2026-03-08_Race/TimingData.jsonStream`; cached response status is 200 and raw body SHA256 is `a2521be4b468f9ec4c61211558521c993269eb34c24c600e1fa3c90ebb251c8d`. Its July cache creation timestamp is the historical HTTP retrieval time, not the March sector publication or client receipt time.

The installed primary source explains why processed lap rows cannot supply the issuance clock:

- `fastf1/_api.py:126–135` explicitly describes guesses, removals and timestamp postprocessing.
- `_api.py:387–429` scans future lap boundaries before assigning data; lines 453–466 allocate late sector updates and initially save the raw packet time.
- `_api.py:634–715` synchronizes lap boundaries using sector durations, propagates corrections backward/forward between laps and replaces sector timestamps with reconstructed earlier values.
- `fastf1/core.py:1549–1602` constructs `LapStartTime` from processed preceding laps and inferred restart/pit-out logic. It is not a retained independent raw start receipt.

In the actual sample, all 1,984 finite processed S1/S2 values match a raw packet value within ten seconds. **1,949 processed timestamps precede their matching raw update**: median raw-minus-processed difference 0.127 seconds, maximum 0.543 seconds. For driver 63, lap 2 S1, processed time is 3862.530 while the raw update carrying 29.753 seconds arrives at stream time 3862.721. The subsecond size in this race does not certify a universal latency bound or remove the full-session processing dependence.

The main HTTP cache has nine 2026 race streams, ranging from 5.25 to 7.32 MB, median 6.33 MB. The separate `data/f1/performance_20260907/live_recent_approved/isolated_fastf1_cache/fastf1_http_cache.sqlite` contains four more 2026 race streams: Belgium, Hungary, the Netherlands and Italy, approximately 5.62–7.49 MB each. No 2022–2023 timing stream was found in these caches. The one-session parser plus processed/raw comparison took about 1.6 seconds on one CPU; this is a local input probe, not an inference benchmark.

A minimal discovery acquisition can reuse the already verified 44-event weather manifest's **named Race session paths**, replacing `WeatherData.jsonStream` with `TimingData.jsonStream`. Do not remap 2023 by provider meeting number. Download one 2022 and one 2023 race first, inspect counter/stage/revision behavior, then freeze the parser before the remaining events. The public mirror is the existing acquisition route; availability of its individual discovery TimingData URLs has not yet been checked. Preserve original raw bytes, actual URL, HTTP retrieval time, status and hashes in a new isolated directory. Do not call full `Session.load` or fetch car/position telemetry. Read line-by-line, retaining compact driver state and sector events, rather than a season of nested packet dictionaries. At the cached median size, 44 races imply roughly **279 MB uncompressed timing data** and around 2.4 million packets if this sample is representative. Wire size and network time remain unmeasured. The resulting two-sector issuance table would be roughly 87,000 rows at this sample's density. These are acquisition estimates, not coverage guarantees.

Add the small `SessionStatus` stream to identify running/end phases and detect incomplete tails. Existing observed `TrackStatus` acquisition can supply strictly prior neutralization flags. `TimingAppData` is optional only if current tyre/stint features are introduced; the reduced first experiment should avoid requiring it. Never recover a current tyre state from a future completed-lap CSV row. Likewise, the current HGB's final `IsAccurate` and other reconstructed fields cannot simply be declared available at a sector checkpoint. The first comparison needs a baseline built from the same raw prefix; any comparison to carried legacy HGB should explicitly retain its older information and recorded-data limitations.

A same-product experiment must preserve the **same driver's next eligible clean completed lap strictly after the sector checkpoint**, potentially skipping the current numbered lap. The preferred contract is:

1. Issue after the first positive S2 value update for a driver's current causally tracked lap epoch, with an observed lap counter and an as-of running state. Maintain the issuer from raw packet sequence, counters and sector resets; do not use future lap endpoints to repair its history. Keep revisions and ambiguous/reset cases in the ledger. This sample's simple counter keys are only a feasibility diagnostic, not a completed robust parser. Unknown count can be an explicit warm-up status determined at issuance.
2. Timestamp the forecast at the raw packet timestamp plus a fixed assumed processing/receipt delay, predeclared before scoring; test zero, one and three seconds without selecting the best delay. A replay after an assumed delay may use only packets received by that checkpoint. Equal-time batches need a fixed policy. Late or revised records can change future state but never retroactively change a saved forecast.
3. Freeze the last **already issued HGB point** before the checkpoint as the comparator. Both forecasts target the first subsequently completed lap satisfying the original recorded eligibility definition; the current lap's future cleanliness must never select an issuance. The original HGB point is carried forward without refitting or rewriting its features after seeing sector updates. Retain its original issue time and lap, the new sector issue time, model identities and every availability decision. Never attach a finalized current-lap CSV row at S1/S2.
4. Preserve the entire issuance ledger, including forecasts whose driver never produces another eligible lap. Resolve targets in a separate forward outcome pass; do not merge with future clean laps using an inner join and call the resulting subset the full population. Report event-balanced MAE among matched outcomes **explicitly conditional on a later eligible lap existing**, plus eligible-target-balanced MAE so repeated S1/S2 forecasts do not dominate, matched/issued counts, and all unmatched terminal/missing-feed cases. The original point estimand is undefined when no future eligible lap exists: there is no honest finite point-MAE contribution to invent for those rows. An all-issued scored product therefore also needs a predeclared probability of another eligible completion before session end and a conditional duration distribution, evaluated by the proper joint log score `−log(1−p)` for no eligible completion or `−log(p)−log f(y)` for a completed eligible target. Archive truncation remains censored, not a confirmed no-completion outcome. This extension is a separate product/evaluation contract requiring an explicit comparison; point-only research must state its conditional scope.
5. Include a strong remainder-based point comparator at the same new checkpoint: current observed sectors plus a causal estimate of remaining sectors when the current lap proves the next eligible target, with an as-of eligibility/transition mechanism for cases where it does not. The model cannot use eventual cleanliness to choose that branch. Maintain recent own-sector estimates and strictly earlier field updates with explicit source times. Report errors and lead time for all matched targets, current-lap versus later-lap targets as **outcome diagnostic subsets**, and the matched/issued gap. Reduced remaining uncertainty is valuable new information, but a gain over a much earlier carried forecast is not an improvement at the original issuance. Report the original eligible-issuance benchmark separately and unchanged.

The sample's capped counter-time counts demonstrate that raw feed outcomes can be measured without future clean-lap selection. They are **not a proposal to substitute time-to-counter for the requested next-eligible-lap target**. A capped completion-time product could separately define a finite loss for all observed 180-second windows and interval bounds for truncated windows, but it requires its own product comparison and must not be presented as progress on the existing estimand.

There is a remaining baseline-readiness constraint. The archived raw TimingData feed does not contain the finalized `IsAccurate` flag used by the legacy encoder. Exact original `Stint`, `Compound`, `TyreLife` and `FreshTyre` availability also requires a separately replayed TimingAppData stream; their final lap-CSV values are not a receipt ledger. Using the prior frozen HGB forecasts is a valid **shared recorded-reference diagnostic** only if that inherited limitation is stated; assigning their recorded lap-end times to historical live receipt times does not establish end-to-end causality. A strictly causal deployment comparison needs either actual logged HGB output/receipt times, or an explicitly versioned as-of reconstruction of completed-lap eligibility and tyre state, checked against raw records and acknowledged as a changed input contract. The latter cannot silently be called exact canonical HGB parity. No future target flag may repair the baseline history during replay.

Readiness decision: **go for a small raw-parser/input pilot; do not yet fit a model claiming fully causal parity with the original HGB**. The sector information itself is present, useful and cheap. Before model fitting, settle the prior-point availability contract, lap-epoch handling, target existence accounting and stronger same-checkpoint comparator. Two discovery races are enough for the first parser audit; downloading all 44 race streams is not yet necessary.

Raw archive timestamps provide recorded stream chronology, not verified historical **client receipt** chronology. The installed `fastf1/livetiming/client.py:126–143` updates an in-memory last-message time but writes the supplied message without persisting a separate client receipt timestamp. A prospective collector should record both raw feed time and local UTC/monotonic receipt time, plus sequence and reconnect gaps. That is required for a genuinely measured end-to-end latency claim. This feasibility review supports a causal recorded-stream experiment now and a prospective receipt audit later; it does not certify historical network availability.

The information upgrade is attractive because the current car has already supplied fresh pace measurements with roughly 37 seconds of remaining lead after S2. The engineering cost is moderate. The principal risks are lap-epoch/revision handling and target comparability, rather than data volume. No new prediction gain or promotion is claimed here.
